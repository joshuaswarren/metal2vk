The fragment layout the shim implements (MLX steel NAX, uzu `MxuFragmentOps<true>`, flashnext and nemotron all pack for it; verified bijective against all four call sites): lane l of a 32-lane group holds x = (l & 8) + 4 * (l & 1), y = 4 * ((l >> 4) & 1) + ((l >> 1) & 3); element i of a 16-row tile is at row y + 8 * ((i >> 2) & 1), column x + (i & 3) + 16 * (i >> 3); with `execution_simdgroups<N>` the 32-lane groups tile columns, or rows for 32-row tiles. uzu's `MxuStrictFragmentOps` packs for the other (strict) hardware layout; under the emulation its mma results land permuted - valid modules, Apple-relative numerics differ.

The clspv bfloat diagnostic loop this slice reported (class 2): the modules reached clspv with the LLVM bfloat type still in them and clspv looped printing `Err: SrcTy = bfloat - DstTy = i16 - CstVal = 16` (~1.4M lines in 120 s). The bfloat_to_i16 pass clears it - after the pass no bfloat type remains (only mangled names and metadata strings) and those entries fail fast on class 3's `Invalid bitcast` instead of timing out; the pass is not missing a construct for these modules.

Untyped-pointers capability on the qmm family (closed this slice): the producer's GEP case classifies any GEP with a non-zero first index as OpPtrAccessChain and switches on the storage class; the switch has no Function/Private case, so the simdgroup accumulator tiles (vector GEPs with a non-zero first index on private memory) reached `default: llvm_unreachable`, which Release builds compile out. The miscompiled fall-through executed the untyped needs_array path with --untyped-pointers OFF (verified at runtime: `Option::UntypedPointers()` returns false for these compiles) and declared `OpCapability UntypedPointersKHR` plus `OpUntypedAccessChainKHR` on otherwise typed modules - which is why gating the two predicate sites on the option (apply-untyped-gep-predicate, apply-untyped-capability-gate) changed nothing. `apply-producer-private-ptr-access-chain.py` adds the Function/Private case (legal typed OpPtrAccessChain; the existing !untyped path already requests VariablePointers). A build race hid the earlier gate: the shipped covptr binary's SPIRVProducerPass.cpp.o finished 37 s after the gate edit landed, so that binary never contained the gate; every measurement above comes from a clean rebuild of the patched source.

tf_gather_qmv OpAccessChain type mismatch (closed this slice): runOnImplicitCasts folded pairs like `gep i8, (gep i32 base, %a), %b` by regenerating indices at the inner element's granularity, and `GetIdxsForTyFromOffset`'s dynamic path divides (%b / 4), dropping the sub-word remainder; the reverse conversion multiplies back, so the same pair re-folded every outer-loop iteration, appending one lshr/shl link per pass (the module diff between invocations shows a chain of ~100 alternating `lshr i32 %x, 2` / `shl i32 %x, 2` nodes where the source had one byte index) and decaying the offset, which the iteration-hash guards cannot catch because the module genuinely changes each round. `apply-implicit-casts-lossless-merge.py` merges such pairs at the finer of the two granularities - both offsets scale UP to that unit, a multiply, which is lossless - leaving the byte-granular chain that ReplacePointerBitcastPass lowers into typed word loads; aggregate and unsized types keep the old path.

spirv-val loop structure, reopened and closed by cov-loop2: the closure row above was not stable across clspv binaries - the cov-loop measurement reported 0, while the committed post-cov-cap sweep results (a clean f2b01dd6 build of the 15-patch CI chain) list 32 entries failing on exactly this message (16 flashnext/lane_qmm_bytes_grouped, 4 prefill/attention_nax, 11 prefill/gemm_nax, uzu gdn/chunked/output_and_state v1). The shape is a refinement of the one continue-latch fixed: after StructurizeCFG, the inner loop's merge block is again the enclosing loop's latch (the SPIR-V continue target), but this time the inner loop reaches that latch through a grandparent loop (not the immediate parent) or through one of several exit edges, so the old isolateContinue check - unique exit vs immediate parent's latch - never fired; on the gdn input IR no such block pair exists at all, StructurizeCFG's flow blocks create it. The validator rejects the module because the loop construct of the enclosing loop excludes blocks dominated by its continue target, so the inner merge lands in the continue construct instead of the construct (SPIRV-Tools Construct::blocks: a loop construct excludes blocks dominated by the continue target). `apply-isolate-continue-exits.py` widens the same split to every exit block of the inner loop against the latch of every enclosing loop: inner-loop edges into the shared block are redirected through a fresh fall-through block that becomes the inner merge inside the enclosing construct, and the old block keeps the latch role and the continue target. Not covered: loops without a unique latch, where the producer's continue scan picks the last non-header block that this pass cannot predict (no current entry lands there). Measured on the 16-patch chain: the class goes 32 -> 0 with no other entry changing state.

Order of work: 4, 6 and 7 first (shim only, one commit each), then 3 and 5 (one IR pre-pass), then 2, with 1 following the coopmat slice.

## Rules for this file

- A row closes when the sweep shows its entries valid, not when a fix is written.
- A class that splits gets a new row; counts are re-taken from the last sweep, so rows can change when an earlier class lands.
- A fix that makes SPIR-V valid but wrong is a regression; the run stage (`sweep/m2v_sweep_run.py`) is where those show.
